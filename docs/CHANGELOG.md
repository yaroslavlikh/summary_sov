## 2026-09-09 (независимый gold-candidate builder, чтобы разорвать circular evaluation)

Прямое следствие находки из записи ниже: production `upsert_state` extraction нельзя использовать как источник gold-датасета для оценки самой extraction — круговая оценка. Новый [research/gold_candidate_builder.py](../research/gold_candidate_builder.py) — полностью read-only (никаких записей в `memory_facts`/`chat_context`/`chat_moments`), два независимых пути обнаружения:

- **Путь A** — существующие 644 `chat_moments` → hybrid FTS+vector retrieval сырых сообщений (переиспользует `_or_query`/`_rrf` из [llm/graphs.py](../llm/graphs.py)) → LLM проверяет, действительно ли ретрив подтверждает исходный moment, и классифицирует `fully_supported/partially_supported/unsupported`.
- **Путь B** — независимый recall-проход по сырой истории чанками по 40 сообщений, НЕ завязанный на moments вообще (чтобы не наследовать слепые зоны старой памяти), по 8 категориям (state, durable_person_fact, relationship, commitment, past_event, opinion, running_gag, group_lore) + other.
- Дедуп по косинусной близости эмбеддинга claim'а (порог 0.92) между обоими путями.
- **Реальная находка при первом прогоне recall-промпта пути B**: без явного ограничения модель предлагала факт почти на КАЖДОЕ сообщение (тривиальщина вроде "The summary feature now works", на английском вместо русского) — промпт переписан с явным требованием долгосрочной ценности ("будет ли это полезно через недели"), явным списком исключений (одноразовые реплики, короткие реакции, шум) и явным ожиданием 0-5 находок на 40 сообщений (а не по находке на сообщение). После правки — реалистичный результат вида "Ретивов умер", "Ярик Лихачев усилил шифрование сообщений, но сообщения Гордея остаются незашифрованными".
- **Реальный прогон по всей истории (1149 сообщений, 644 moments)**: путь A — 16 подтверждённых кандидатов из 644 moments; путь B — 65 кандидатов из 29 чанков. Итого 81 сырых → 76 после дедупа → все 76 включены в Markdown review sheet (`/tmp/gold_review_sheet.md`), т.к. пул уже в целевом диапазоне 50-70 и дальше урезать по subject-cap означало бы просто терять валидные кандидаты без пользы.
- Формат review sheet — чекбоксы `accept/edit/reject/ambiguous attribution` на каждый кандидат, с минимальным source-сетом и локальным контекстом вокруг первого источника, без `retrieval_cues`/eval-вопросов (это следующий шаг, после заморозки gold).

## 2026-09-09 (Stage 1 hardening, вдогонку: resolver rewrite + dry-run по всей истории)

- **Резолвер переписан на source-author-first, curated-приоритет убран.** Первая версия hardening'а (см. запись выше) вводила "curated identity побеждает uncurated" — это само по себе опасно: если в чате реально два "Игоря", такой приоритет тихо выбирает "любимого" curated-участника вместо честного ambiguous, ровно тот attribution collapse, который вся система должна предотвращать. Новый [participants.py](../participants.py): `resolve_subject_for_fact(chat_id, name_hint, source_message_ids)` — если имя совпадает с автором ИСХОДНОГО сообщения (self-referential: "я"/своё имя) — резолвится детерминированно в этого автора, без всякой проверки на неоднозначность (мы точно знаем, кто написал). Если сообщение — reply, и имя совпадает с автором reply-target — тоже резолвится через это. Только если ни один сигнал не применим — обычный поиск по имени среди ВСЕХ известных участников на равных правах (curated и uncurated). `resolve_participant_key` (плоский поиск по имени, без спецлогики) — отдельная, более простая функция для general-purpose использования.
  - Реальная проверка: "Игорь учится в Мирэа" (сказано САМИМ Goshanka200) теперь резолвится в него детерминированно через авторство, даже при наличии другого некурированного "Игоря" в чате.
  - 2 новых теста (13 всего, все зелёные): self-referential резолвится через автора; третье лицо с реально неоднозначным именем (не автор, не reply-target ни для кого) — отклоняется, не резолвится через curated-приоритет.
- **Dry-run extraction по всей реальной истории (1081 сообщение, 7 батчей), дважды.** `research/dry_run_extraction_full_history.py` доработан: убран Langfuse-трейсинг (сломал батч на первом прогоне таймаутом), добавлено логирование ВСЕХ 4 тулов по батчу (не только upsert_state — чтобы отличить "экстракция сломалась вообще" от "именно state-фактов не нашлось").
  - **Честный итог: 0-1 upsert_state кандидат на два независимых прогона одних и тех же данных** (по сравнению с целью документа "хотя бы 30"). `chat_context` — 1-2 строки из 1081 сообщения. `chat_moments` — 0 в обоих прогонах.
  - Разница между прогонами (1 vs 0 на одних данных) — отдельная, важная находка: свободный tool-calling нестабилен в решении звать ли тул вообще, не только в том, что решить, если решил звать.
  - Решение по этой находке: НЕ строить gold-датасет через production extraction (circular evaluation — extraction сам является тестируемой частью). Дальше — независимый gold через существующие 644 `chat_moments` (как поисковые подсказки, не источник provenance) + отдельный проход по сырым сообщениям с более широким набором категорий (state, durable_person_fact, relationship, commitment, past_event, opinion, running_gag, group_lore, не только 6 текущих state_key). Плюс redesign production extractor: forced structured JSON вместо free-choice tool-calling, батчи 30-50 вместо 180, temperature=0.

## 2026-09-09 (Stage 1 hardening)

Прямое следствие реального прод-бага (self-referential memory_target не резолвился) — усилил весь write-контракт `upsert_state`, прежде чем идти дальше к retrieval/reranker'у:

- **Нормализация человека** — новый [participants.py](../participants.py): `resolve_participant_key(chat_id, name_hint)` резолвит свободный текст ("Миша"/"Мишаня") к стабильному `participant_key` (username, либо нормализованное имя) среди РЕАЛЬНЫХ участников этого чата. Неоднозначный/неизвестный subject → `upsert_state` кидает `ValueError`, факт НЕ пишется автоматически (не молча привязывается к случайному ключу).
- **`observed_at` считается сервером** — `MAX(source messages.message_date)`, дате от модели больше не доверяем вообще (параметр убран из сигнатуры).
- **`state_key` ограничен фиксированным набором** ([memory_facts.py](../memory_facts.py) `ALLOWED_STATE_KEYS`): `current_location, work_study, availability, relationship, preference, plan`. Всё остальное → `state_key=None`, факт всё равно пишется, но не supersede'ит.
- **Citation label vs реальный ID разделены** — `/summary` для пользователя снова видит `[1..N]` (не деградирует читаемость огромными message_id), а extraction-проход получает отдельный `extraction_lines` с явным `{message_id=X}` тегом на каждой строке ([handlers/handlers.py](../handlers/handlers.py), [llm/prompt.py](../llm/prompt.py)).
- **Dry-run extraction** — `upsert_state`-тул в [llm/graphs.py](../llm/graphs.py) принимает `write_state` колбэк (`build_summary_graph`/`run_summary_graph`), по умолчанию — реальная запись, для исследования — сборщик в JSON без единой записи в БД.
- **11 тестов** ([tests/test_memory_facts.py](../tests/test_memory_facts.py), unittest, реальный sandbox-Postgres): пустой/чужой provenance отклоняется, неизвестный subject отклоняется, алиасы резолвятся в один ключ, невалидный state_key занижается до None, новое состояние supersede'ит старое, `state_key=None` копится, разные люди не supersede'ят друг друга, `observed_at` берётся из сообщений, истёкший факт не возвращается, source вне текущего batch отклоняется. Все зелёные.
- Схема: новая колонка `memory_facts.subject_display` — человекочитаемое имя рядом с ключом, чтобы retrieval не делал лишний lookup.
- `research/dry_run_extraction_full_history.py` — прогон extraction по всей реальной истории (sandbox, `write_state=collect`, ничего не пишет в прод) для сбора gold-датасета кандидатов.
