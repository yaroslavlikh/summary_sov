## 2026-09-09 (oracle-memory retrieval: шаг 1 из плана baseline vs oracle /ask)

После honest-recall находки (extraction — не главная идея статьи), новый порядок экспериментов: (1) oracle-memory retrieval, (2) датасет memory-dependent вопросов, (3) paired baseline vs oracle /ask, (4) no-regression check на существующем ask-pipeline-eval-run. Это шаг 1.

Новый [research/oracle_memory_eval.py](../research/oracle_memory_eval.py) — использует замороженные 44 gold-факта как oracle-память (идеальная precision/recall by construction), намеренно изолируя качество retrieval/rerank/generation от качества extraction (которое уже честно измерено как слабое место — 23% fully-recovered). Sandbox-схема с реальными сообщениями/chat_context/chat_moments (копия, до `HISTORY_CUTOFF_MESSAGE_ID`) + 44 факта в `memory_facts`. Два графа на одной и той же sandboxed среде, отличаются только последним узлом:
- `build_ask_graph_baseline()` — те же узлы, что в продакшн `build_ask_graph_merged()` (импортированы напрямую, не переписаны).
- `build_ask_graph_oracle()` — тот же граф, только `generate_answer` дополнительно подмешивает `memory_facts.search_facts_by_vector` в `group_context`, аналогично тому, как туда уже подмешиваются `chat_moments`.

MVP — только vector-ретрив (`memory_vector` branch из research doc, Sec 5.2); entity-based (`get_active_facts`, Sec 5.3) — следующая ablation-переменная, не подключена.

По пути найден и исправлен баг: LangGraph инжектит `config` в узлы графа по имени/типу параметра (`RunnableConfig`) — верхнеуровневый `import config` (для dotenv) в скрипте случайно затенял ожидаемое имя, из-за чего первая попытка падала с "missing required positional argument".

**Smoke-тест (3 вопроса, не полноценный eval)**: Крым — baseline теряет атрибуцию ("Крым — Россия"), oracle сохраняет ("Ярик считает, что..."); Игорь/Ксюша — оба одинаково верны (нужное сообщение и так попало в окно ретрива, память не понадобилась); VPN — оба верны, oracle надёжнее (добавляет "Sota" вне зависимости от того, попадёт ли конкретное сообщение в reranked-окно). Честно: 3 вопроса — не доказательство, это подтверждение, что механизм работает и стоит строить датасет (шаг 2).

## 2026-09-09 (первый forced-extractor отчёт скорректирован: source coverage ≠ fact recall)

Human review первого отчёта нашёл, что `loose`/`strict` метрики переобещали. Новый [research/reevaluate_forced_extractor.py](../research/reevaluate_forced_extractor.py) пересчитывает метрики из УЖЕ ЗАКЭШИРОВАННОГО вывода extractor'а (`/tmp/forced_extractor_output.json`) — extractor НЕ перезапускался, LLM-вызовов ноль:

- **`loose` переименован в `source_any`** и явно помечен как потолок (ceiling), не recall — кейс №67 "совпал" только потому что один извлечённый кандидат случайно процитировал то же message_id, при этом описывая три СОВЕРШЕННО другие вещи (портрет Игоря, Langfuse) вместо реального факта про тестирование бота Яриком.
- **`strict` считал `subject_key=None` на обеих сторонах совпадением** — двое независимых "не смог резолвить" не значит "согласны, кто субъект". Исправлено: `subject_match` теперь True только когда ОБЕ стороны резолвились и совпали.
- Добавлены `source_all` (все source gold покрыты одним кандидатом extractor'а — важно для multi-source), `claim_equivalent` и `attribution_preserved` — вручную размечены для всех 19 source_any-совпадений (маленький, полностью читаемый список, не автоматика на все 44), с обоснованием по каждому кейсу.
- **Скорректированные цифры**: source_any 43% (19/44, потолок) → subject_match 27% (12/44) → claim_equivalent 32% (14/44) → **честный "fully recovered" (claim_equivalent И subject_match): 23% (10/44)**. Multi-source: 0/6 строго (единственный content-совпадающий кейс №58 "капитан/вискарь" проваливает subject_match — известный пробел резолвера на английской транслитерации "Sasha Tigmen", не новая проблема).
- Найдены конкретные новые кейсы epistemic-регрессии в extractor'е: №43 — extractor присвоил Ване прямую речь, хотя источник это пересказ Тигмена (мисатрибуция хуже, чем у gold); №45 — extractor заново потерял атрибуцию и субъект (Игорь→Ксюша) — тот самый баг, который gold review специально фиксил для этого пункта.
- **Frozen cutoff добавлен** в [research/forced_extractor_eval.py](../research/forced_extractor_eval.py): `HISTORY_CUTOFF_MESSAGE_ID = 73100` (макс. реальный message_id первого прогона) — без этого будущий перезапуск через недели молча захватил бы выросший чат, и результаты перестали бы быть сравнимыми. По пути найдена (не тронута, вне скоупа) одна аномальная строка `message_id=999999999, is_bot=TRUE` — не влияет ни на один прогон, так как везде фильтруется `is_bot=FALSE`.
- `11/24 rejected resurfaced` оставлено как есть — отдельный сигнал, не precision.
- Отчёт — `/tmp/forced_extractor_report_v2.md`, не в git.

## 2026-09-09 (forced extractor построен и измерен против заморозенного gold)

Новый [research/forced_extractor_eval.py](../research/forced_extractor_eval.py) реализует то, что было запланировано ещё до заморозки gold: forced JSON output вместо free-choice tool-calling, батчи по 40 сообщений вместо 180, temperature=0, ОДИН проход без отдельной verify-стадии (это и есть проверяемый механизм) — с детерминированной валидацией после генерации (source_message_ids сверяются с батчем, subject резолвится через `resolve_subject_for_fact`, без записи куда-либо). Промпт почти дословно взят из откалиброванного gold-mining Path B — изолирует именно тот вопрос, который стоял в плане: достаточно ли ОДНОГО дешёвого forced-JSON прохода без дорогой отдельной verification-стадии. Читает `/tmp/gold_facts.jsonl` с проверкой sha256-checksum (отказывается работать, если заморозенный файл изменился).

Метрика — пересечение `source_message_ids` (не текст claim: два независимых прогона никогда не совпадут дословно), loose (пересечение id) и strict (id + совпадающий `subject_key`).

**Честный результат первого прогона** (30 батчей, 73 кандидата):
- Recall на 44 known positive: **43% loose (19/44), 34% strict (15/44)**.
- Recall на 6 multi-source positive: **33% (2/6)**.
- Rejected-кандидатов воспроизведено снова: **11/24**.
- Улучшение относительно free-choice tool-calling (0-1 кандидат на весь прогон, см. запись про `dry_run_extraction_full_history.py` выше) — но далеко не полное восстановление.

Качественные находки:
- **Резолвер нестабилен между независимыми прогонами не из-за самого резолвера, а из-за входного текста**: `resolve_subject_for_fact` детерминирован для одного и того же `subject_raw`, но МОДЕЛЬ на двух прогонах предлагает разный `subject_raw` для одного и того же факта (напр. gold `subject="Саша Тигмен и Лизка"`, extractor не резолвил "Ваня"/"Ксюша Изюмова" в тех же кейсах) — отсюда часть loose-но-не-strict совпадений (#43, #45, #29, #40, #58, #67).
- **Круговая память из скриншота бота воспроизвелась снова**: rejected-кандидат №63 (портрет Игоря, реконструированный из скриншота ответа самого бота — известный пробел, отмеченный ещё в v2.1/v2.2 review) resurfaced почти дословно в этом прогоне, из того же сообщения [72983]. Подтверждает, что это не случайность gold-mining прохода, а систематический пробел текущего is_bot-фильтра (фильтрует АВТОРА сообщения, не содержание).
- **Полный пропуск кластера**: сообщение [72178] ("мясцо") — источник сразу 3 gold-фактов (#2, #41, #71) — не породило НИ ОДНОГО кандидата в этом прогоне (не частичное совпадение, а полный ноль на весь батч).
- Отчёт с деталями (все missed/recovered/resurfaced) — `/tmp/forced_extractor_report.md`, не в git.

Не полноценный precision/recall (история не размечена исчерпывающе, оценивается только против 44+24 размеченных), но первый честный эксперимент с реальными числами — как и планировалось.

## 2026-09-09 (gold заморожен: схема достроена, checksum зафиксирован)

Перед заморозкой пользователь явно подтвердил все 11 правок (4 edit + исключение №31 + 7 attribution-fix) и попросил достроить схему `gold_facts.jsonl` без LLM. [research/build_gold_facts.py](../research/build_gold_facts.py) доработан:

- `label: hard_negative` → `label: rejected_candidate` — "human rejected" не то же самое, что "confirmed negative для оценки extractor'а"; переименование убирает лишнее заявление.
- Добавлены `original_claim` (текст до edit/attribution-fix, для всех записей, не только изменённых), `human_decision` (сырое accept/edit/reject, отдельно от производного `label`), `observed_at` (диапазон дат source-сообщений, парсится из sheet), `subject_key` — пересчитан заново через `participants.resolve_subject_for_fact` (детерминированный DB lookup, без LLM, без записи) вместо доверия отображаемому в sheet тексту, чтобы `gold_facts.jsonl` не зависел от возможно устаревшего порядка в JSON-кэше.
- `subject_ambiguous` → `subject_unresolved` — бот/GPT/группа/третьи лица не являются "неоднозначными людьми", просто не резолвятся к участнику чата.
- Добавлен sha256-checksum файла (`/tmp/gold_facts.sha256`), фиксирующий именно эту версию как замороженную.
- Финальные цифры не изменились: 44 positive (6 multi-source), 24 rejected_candidate, 4 исключено. 0 случаев `subject_key=None` при `subject_unresolved=False` (т.е. резолвер либо честно резолвит, либо честно помечает неразрешённость — расхождений не найдено).
- **Gold заморожен.** Следующий шаг — forced extractor: recall по 44 known positive, ложные срабатывания на 24 rejected_candidate, отдельно результат на 6 multi-source. Не полноценный precision/recall (история не размечена исчерпывающе), но первый честный эксперимент.

## 2026-09-09 (критический баг: dedup смешал subjects -> v2.2 + reprocess-cached + тест)

Третий review нашёл реальный critical bug в v2.1: `_dedupe()` мержил кандидатов ТОЛЬКО по похожести эмбеддинга claim'а, без проверки subject. Реальный кейс: Ярик `[71811] Крым России` и Тигмен `[71827] Крым абсолютно точно часть России` слились в одного кандидата с `Subject: Ярик Лихачев`, куда попал и source-message Тигмена — то есть provenance одного человека молча приписан другому. Ровно тот attribution collapse, ради изучения которого весь этот pipeline строится, воспроизведённый инструментом, который должен его предотвращать.

Исправлено в [research/gold_candidate_builder.py](../research/gold_candidate_builder.py):

- **`_dedupe()` теперь гейтится по `subject_key` (fallback normalized `subject_raw`) И `kind`** — эмбеддинг-схожесть сама по себе больше недостаточна для мержа, только внутри одного и того же субъекта и вида факта. Это floor, не гарантия (два противоположных мнения ОДНОГО человека всё ещё технически могут слиться, если эмбеддинги окажутся близки — на реальных данных этого не случилось, но не полагаемся на удачу).
- **Для текущего маленького пула (72) dedup вообще выключен** (`apply_dedup=False` по умолчанию и в `run()`, и в новом `reprocess_cached()`) — при пуле такого размера человек мержит дубли вручную безопаснее, чем эвристика. Пересобранный sheet: снова 72 кандидата (было ошибочно 71 после бажного мержа).
- **Новый `--reprocess-cached` CLI-режим** (`python3 research/gold_candidate_builder.py --reprocess-cached --input=... [--dedup]`) — ноль LLM-вызовов, только subject resolution (детерминированный DB lookup) и рендер. Раньше v2.1 был получен разовой ручной командой в консоли, что не воспроизводимо и не проверяемо; теперь это первоклассный режим.
- **`run()` больше не перезатирает исходный кэш** — LLM-верифицированные кандидаты пишутся РОВНО ОДИН раз в `VERIFIED_CACHE_PATH` (`/tmp/gold_candidates_verified.json`), reprocess_cached() их только читает, output пишет в отдельные файлы (`_processed.json`, `.md`). Раньше `run()` дампил `deduped` поверх файла с именем `raw_v2` — потенциально уничтожая исходный pre-merge кэш при повторном запуске.
- **Новый тест** [tests/test_gold_candidate_builder.py](../tests/test_gold_candidate_builder.py) (unittest, БЕЗ Postgres/LLM — только локальная embedding-модель): 4 кейса, включая точно этот баг с реальными claim/id (Крым, Ярик vs Тигмен) — похожие claims разных субъектов остаются раздельными кандидатами с собственным provenance; тот же subject+kind по-прежнему мержится (регрессия на полезное поведение); разный kind у одного subject не мержится; unresolved subjects (`subject_key=None`) не путаются друг с другом просто потому что у обоих `None`.
- v2.2 (`/tmp/gold_review_sheet.md`, не в git) — 72 кандидата, без dedup, с перенесёнными (не пересчитанными) contradiction-флагами по Израилю (3 кандидата) — готов для ручной разметки.

## 2026-09-09 (v2 review: остановили regeneration, докрутили без LLM -> v2.1)

Второй человеческий review (уже v2) дал вердикт: candidate mining задачу выполнил, дальше — не перегонять миксер ещё одним LLM-проходом, а переходить к ручной разметке. Из списка находок исправлено только то, что чинится БЕЗ нового LLM-вызова (переобработка уже закэшированных 72 верифицированных кандидатов из `/tmp/gold_candidates_raw_v2.json` чистым Python + read-only DB):

- **Резолвер использовался не тот** ([research/gold_candidate_builder.py](../research/gold_candidate_builder.py) `_resolve_subjects`): вызывался `resolve_participant_key` (плоский поиск по имени), хотя для self-report'ов уже есть source-author-aware `resolve_subject_for_fact` (тот же, что использует `upsert_state`). Замена детерминированная, без LLM — не может резолвить МЕНЬШЕ случаев, только больше. Реальный эффект: неразрешённых "Игорь" было 3, стало 1 (два self-report'а типа "Все женщины без ума от меня" теперь резолвятся в автора сообщения; третий, "Ксюша сейчас хороша", остаётся честно неоднозначным).
- **Дедуп выбрасывал provenance**: `_dedupe()` при совпадении по эмбеддингу claim'а просто удалял дубль. Теперь СЛИВАЕТ — union `source_message_ids`, оба `discovery_paths` сохраняются, support берёт более сильный из двух. Совпадение путей A и B на одном факте — сигнал, не мусор (в этом прогоне пересечений не нашлось: Path A и Path B пока покрывают разные факты).
- **Несогласованность target/фактического размера файла** (было: `target=70`, в файле 71 кандидат): убран отдельный глобальный `target`-порог поверх per-subject cap — он не нёс смысла при пуле такого размера и создавал путаницу. `_select_best` теперь просто капает по subject (fallback на raw), без второго конфликтующего порога.
- **Время не показывалось**: `message_date` уже читался в `_real_rows`, но не выводился. Добавлена строка `Observed at (source message dates)` — диапазон дат по всем источникам кандидата. Полноценный `temporal_scope` (persistent/transient/event) требует суждения и оставлен на ручную разметку, как и просили.
- **Локальный контекст только вокруг первого источника**: для multi-source кандидатов это скрывало реальный разрыв между источниками (кейс "№65 объединяет две реплики с большим разрывом"). Новая `_local_context_multi` показывает контекст вокруг ВСЕХ источников кандидата, смёрженный и отсортированный — большой разрыв теперь виден напрямую в контекстном блоке.
- **Contradiction-флаги перенесены, не пересчитаны**: единственный найденный ранее LLM-подтверждённый case (противоположные мнения об Израиле, 3 кандидата) перенесён вручную по совпадению текста claim — новый contradiction-проход не запускался (это тоже был бы LLM-вызов).
- **Sheet сгенерирован БЕЗ per-subject cap для этой раздачи**: после нормализации резолвером выяснилось, что Тигмен и Ярослав реально доминируют пул (20 и 18 из 71 — настоящий, не артефактный перекос данных). Cap=8 по умолчанию (для будущих больших корпусов) молча убрал бы 22 кандидата из ручного review без ведома человека — для этой раздачи вызван с `max_per_subject=100` (фактически без cap), все 71 идут на разметку, а не пред-отфильтрованные скриптом 49.
- Добавлен шаблон полей для ручной разметки прямо в sheet (`memory_worthy`, `assertion_mode`, `temporal_scope`, `subject_type`, `sources_sufficient`, `edited_claim`) — по списку из review, без готовых значений, чисто чтобы разметка не начиналась с пустого листа.

## 2026-09-09 (независимый gold-candidate builder, чтобы разорвать circular evaluation)

Прямое следствие находки из записи ниже: production `upsert_state` extraction нельзя использовать как источник gold-датасета для оценки самой extraction — круговая оценка. Новый [research/gold_candidate_builder.py](../research/gold_candidate_builder.py) — полностью read-only (никаких записей в `memory_facts`/`chat_context`/`chat_moments`), два независимых пути обнаружения:

- **Путь A** — существующие 644 `chat_moments` → hybrid FTS+vector retrieval сырых сообщений (переиспользует `_or_query`/`_rrf` из [llm/graphs.py](../llm/graphs.py)) → LLM проверяет, действительно ли ретрив подтверждает исходный moment, и классифицирует `fully_supported/partially_supported/unsupported`.
- **Путь B** — независимый recall-проход по сырой истории чанками по 40 сообщений, НЕ завязанный на moments вообще (чтобы не наследовать слепые зоны старой памяти), по 8 категориям (state, durable_person_fact, relationship, commitment, past_event, opinion, running_gag, group_lore) + other.
- Дедуп по косинусной близости эмбеддинга claim'а (порог 0.92) между обоими путями.
- **Реальная находка при первом прогоне recall-промпта пути B**: без явного ограничения модель предлагала факт почти на КАЖДОЕ сообщение (тривиальщина вроде "The summary feature now works", на английском вместо русского) — промпт переписан с явным требованием долгосрочной ценности ("будет ли это полезно через недели"), явным списком исключений (одноразовые реплики, короткие реакции, шум) и явным ожиданием 0-5 находок на 40 сообщений (а не по находке на сообщение). После правки — реалистичный результат вида "Ретивов умер", "Ярик Лихачев усилил шифрование сообщений, но сообщения Гордея остаются незашифрованными".
- **Реальный прогон по всей истории (1149 сообщений, 644 moments)**: путь A — 16 подтверждённых кандидатов из 644 moments; путь B — 65 кандидатов из 29 чанков. Итого 81 сырых → 76 после дедупа → все 76 включены в Markdown review sheet (`/tmp/gold_review_sheet.md`), т.к. пул уже в целевом диапазоне 50-70 и дальше урезать по subject-cap означало бы просто терять валидные кандидаты без пользы.
- Формат review sheet — чекбоксы `accept/edit/reject/ambiguous attribution` на каждый кандидат, с минимальным source-сетом и локальным контекстом вокруг первого источника, без `retrieval_cues`/eval-вопросов (это следующий шаг, после заморозки gold).
